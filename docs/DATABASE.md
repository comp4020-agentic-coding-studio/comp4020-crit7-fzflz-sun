# Database

One SQLite file (via `better-sqlite3` + Drizzle ORM) is the app's entire
persistent state — no other store, no client-side state standing in for it.
Locally it's `./.data/app.db` (untracked); on Fly it's `/data/app.db` on the
single mounted volume. Both paths are set by `DATABASE_PATH` (see
`src/lib/db.ts`), which also runs migrations and seeding at boot.

## Tables

```
courses ──< activity_groups ──< sessions ──< allocations >── users >── auth_sessions
                    │                              │            │
                    └──────────< enrolments >──────┘         (self)
```

- **`courses`** — `id, code, name, color`. One row per subject (e.g.
  `COMP1010`). `color` drives the card colour on the grid.
- **`activity_groups`** — `id, course_id → courses, activity_type`. A named
  set of interchangeable candidate sessions within a course (e.g. "COMP1010
  Tutorial"). A student can hold at most one allocation per activity group —
  that's the whole "pick one candidate, the rest disappear" rule.
- **`sessions`** — `id, activity_group_id → activity_groups, day_of_week
  (0=Mon..4=Fri), start_minutes, end_minutes, location, capacity`. One
  concrete meeting time within an activity group.
- **`users`** — `id, username (unique), display_name, password_hash,
  login_enabled (default 1), created_at`. A real login account when
  `login_enabled = 1`; a `login_enabled = 0` row is a historical placeholder
  (see **Upgrading** below) that exists only so old allocation rows still
  point at a real user — it can never authenticate, by construction (see
  `findLoginableUser` in `src/lib/auth.ts`, which filters on the flag).
- **`auth_sessions`** — `id, user_id → users, token_hash (unique),
  expires_at, created_at`. A login session. See **Identity** below for how a
  cookie becomes a `users` row.
- **`enrolments`** — `id, user_id → users, course_id → courses`, unique on
  `(user_id, course_id)`. Which courses a student can see candidates for.
  Written only at seed time this round — there's no registration UI.
- **`allocations`** — `id, session_id → sessions, activity_group_id →
  activity_groups, student_id → users (nullable), user_id (legacy, text, NOT
  NULL), created_at`. One row is one student's pick of one session. Two
  unique indexes matter: `(student_id, activity_group_id)` is the real
  per-user "one pick per group" constraint enforced by the database itself,
  independent of anything the application code happens to check first; the
  older `(user_id, activity_group_id)` index is what enforced that same rule
  before login existed, and is left in place harmlessly. See **The legacy
  `user_id` column** below for why it still exists.
- **`seed_state`** — `key (primary key), applied_at`. One row per named seed
  step once it has run (see **Seeding and upgrading**).

## Identity: cookie → user, every request

1. The browser sends the `session` cookie (`HttpOnly`, `SameSite=Lax`,
   `Secure` when served over https) — a 32-byte random token, base64url,
   generated by `createSession()` in `src/lib/auth.ts`.
2. `src/middleware.ts` runs on every request, reads that cookie, and calls
   `resolveSession(token)`: it SHA-256-hashes the token and looks up
   `auth_sessions.token_hash`. The raw token itself is never stored anywhere
   server-side — only its hash — so reading the database can never hand back
   a token someone could replay (the standard "opaque session token" pattern;
   see the comment above `createSession`).
3. A hit that's expired (`expires_at` in the past) or points at a
   `login_enabled = 0` user is treated exactly like no session at all.
4. The result becomes `context.locals.user` (or `null`) for the rest of the
   request. Every downstream page and API route trusts `locals.user.id` as
   the caller's identity and **never** accepts a `userId`/`studentId` from
   the request body — there is no field in any POST/DELETE body that could
   let one student act as another.
5. Routes not in `PUBLIC_PATHS` (`/login`, `/readme/`, `/api/login`,
   `/api/logout`) 401 (API) or redirect to `/login` (page) when
   `locals.user` is `null`.

## The click-to-allocate request lifecycle

1. Browser: click a card → `fetch("/api/allocations", { method: "POST",
   body: { sessionId } })`, cookie sent automatically (same-origin).
2. Astro's built-in CSRF origin-check middleware runs first, ahead of our
   own: any non-`GET`/`HEAD` request whose `Origin` doesn't match the
   server's own origin is rejected with 403 before it reaches our code.
3. `src/middleware.ts` resolves the cookie to a user; no user → 401 JSON.
4. `src/pages/api/allocations.ts`'s `POST` handler validates `sessionId` is
   an integer, then calls `allocateSession(locals.user.id, sessionId)`.
5. `allocateSession` (`src/lib/db.ts`) runs one `db.transaction()` that:
   looks up the session and its course; 404s if it doesn't exist; checks the
   caller is enrolled in that course (403 `not-enrolled` otherwise — this
   also blocks a direct POST for a session in a course the caller never
   enrolled in, not just what the UI happens to show them); checks the
   caller doesn't already hold a different session in the same activity
   group (409 `already-allocated`; re-posting the *same* session is a silent
   no-op, not an error); counts current allocations against `capacity` (409
   `full`); inserts the row.
6. `better-sqlite3` is synchronous and `db.transaction()` runs the whole
   block on Node's single thread — no other request's JavaScript can run
   between the capacity count and the insert, so two students racing for the
   last seat can't both observe "one seat free": whichever call's
   transaction body runs first commits it, and the second sees the updated
   count and gets `full`. This is what makes the capacity check race-safe
   without any extra locking.
7. Response status maps 1:1 to what happened (`201`, or the specific 4xx);
   the client reloads the grid, which re-derives every card's status fresh
   from the database — there's no cached/optimistic client state to
   reconcile.

Cancelling (`DELETE`) is the same shape minus the capacity/enrolment checks:
`deallocateSession` deletes only the row matching *both* `session_id` and
the caller's own `student_id`, so a request naming another student's
session id deletes nothing (not an error, not someone else's row).

## The legacy `user_id` column

Before login existed, `allocations.user_id` (TS field `legacyUserId`) was a
free-text identity (`"demo-student"`, `"seed-student-7"`) and `NOT NULL`.
SQLite can't relax a `NOT NULL` constraint or change a column's role without
rebuilding the whole table, and rebuilding it under a new foreign key while
enforcing that key against text values that don't correspond to any real
account yet would fail outright. So instead of touching that column:

- It's kept exactly as-is (same DB column, renamed only in the TypeScript
  field to `legacyUserId` for clarity) — zero migration risk.
- A new **nullable** `student_id INTEGER REFERENCES users(id)` column was
  added instead (`ALTER TABLE ADD COLUMN`, always additive/safe in SQLite).
- All application code reads/writes only `student_id` going forward.
  `legacyUserId` is written on every new row purely to satisfy the old
  `NOT NULL` constraint (with the allocating user's username) and is never
  read back by any app code.

## Seeding and upgrading

`runSeed()` (`src/lib/seed.ts`) runs at every boot, right after migrations.
It's a sequence of named, ordered steps — `courses-v2`, `users-v2`,
`enrolments-v2`, `backfill-student-id-v2`, `initial-allocations-v2` — each
wrapped in its own `db.transaction()` and marked done in `seed_state` before
commit. On every subsequent boot, a step whose key is already in
`seed_state` is skipped entirely. This makes the whole thing safe to run
against three different starting points, converging on the same result:

- **A brand-new, empty database** (e.g. a fresh Fly volume): every step
  creates everything from scratch.
- **This prototype's original pre-login volume** (courses/sessions/
  legacy-shaped allocations already exist, no `users`/`auth_sessions`/
  `enrolments`/`seed_state` tables did): `courses-v2` finds the existing
  courses/groups/sessions by natural key (course code, activity type, day +
  start time) via `ensureCourse`/`ensureGroup`/`ensureSession` and adds only
  what's missing (a second activity group per original course, five new
  courses) without duplicating what's already there; `backfill-student-id-v2`
  then walks every existing allocation row with `student_id IS NULL` and
  assigns it a real user (see below).
- **A database that has already been upgraded once**: every step's key is
  already in `seed_state`, so nothing runs a second time — no duplicated
  courses, no duplicated filler allocations, and critically, no restoring an
  `initial-allocations-v2` starting pick that a student has since cancelled
  (that step is guarded purely by its `seed_state` marker, never by
  re-checking the current contents of `allocations`).

`backfill-student-id-v2` maps each distinct legacy `user_id` string still
unresolved to a real `users` row: `"demo-student"` specifically inherits into
`alice` (so the original demo pick becomes a real, login-enabled account's
pick); every other distinct legacy id (`"seed-student-0"`, etc.) gets its own
auto-created `login_enabled = 0` placeholder account, so the row resolves to
a real foreign key without handing out a working login for it.

**To validate an upgrade before trusting it against the real volume:** copy
`.data/app.db` (all three files if present — `app.db`, `app.db-shm`,
`app.db-wal`) to a scratch location, point `DATABASE_PATH` at the copy, and
boot the built server against it. Confirm: pre-existing allocations are
still present with their original session, the new tables/rows exist, and
booting a second time changes nothing further (no duplicate rows, same
`seed_state` contents). Never run this against `.data/app.db` directly, and
never touch the deployed Fly volume by hand — the app's own boot sequence is
the only thing that should ever migrate or seed it.

## Demo accounts

Three real, login-enabled accounts — `alice`, `ben`, `chen` — all share one
password (`DEMO_PASSWORD` in `src/lib/seed.ts`, shown on the `/login` page
itself). Each is enrolled in a different mix of courses and starts with a
different mix of already-allocated / still-open activity groups, so logging
in as each one demonstrates independent, isolated state on the same shared
timetable. Every other `users` row (8 seat-filler accounts, plus one
auto-created placeholder per distinct legacy `seed-student-N` id) has
`login_enabled = 0` and exists only to make seat counts and historical
allocations realistic — none of it is real ANU data or real people.
